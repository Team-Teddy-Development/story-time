## Story
As a client of the hosted story-time MCP, I want each request to start when it arrives, so that a call does not wait or time out while the server is idle.

## Acceptance Criteria
- [ ] Given a server with idle keep-alive connections, when 200 bursts of 5 new connections each send one request, then each request gets its answer in less than 2 seconds

## Notes
Source: ST-143 (2026-11-16). The HTTP front (`native/story-push/src/mcp/http.rs`) uses `tiny_http` 0.12.0, the newest release. Its thread pool loses a wakeup when two connections arrive at almost the same time (`src/util/task_pool.rs`: a worker that `notify_one` woke is still counted in `waiting_tasks`, so the second task is queued for no worker). The queued connection waits until a worker finishes another connection or one more connection arrives.

Seen only in a test stub that `git` reads with several connections (ST-143). Not seen on the deployed server, and not measured there. Possible limit of the effect there: ingress-nginx and the kubelet probes open new connections often, and each one can start the queued one. That is an assumption, not a measurement.

Not decided: replace the listener of the HTTP front, or put a worker pool of our own after `tiny_http`. The first step of this story is a test that shows the wait on the product server.
