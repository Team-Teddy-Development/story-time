## Story
As a team lead, I want each merged pull request to comment on its stories' issues and bring their state in line with the merged cards, so that no story issue stays open after its card is done and every issue shows the pull requests that changed it.

## Acceptance Criteria
- [x] Given a merged pull request whose body has 'Stories: ST-001 (#12), ST-002 (#13)', when the merge-sync workflow runs on a push whose range since the last successful run contains that merge, then each named issue gets one comment that names the pull request and merge commit, and a re-run of the workflow adds no second comment
- [x] Given a merge that changes backlog/ST-001.md to status done, split or archived and issue #12 is open, when the workflow runs, then it closes #12 with a comment naming the merge commit; and given a card that is not done whose issue is closed, then it reopens the issue
- [x] Given a merged card whose issue title, labels or body differ from what story push would write, when the workflow runs, then it updates the issue to match the card on the default branch
- [x] Given a merged pull request that names a story whose card is not done, when the workflow runs, then it does not close that issue and never changes any card's status (story-accept stays the only way to mark a story done)
- [x] Given a repository whose sync setting is off, or a files-only tracker, when the workflow runs, then it writes nothing to the tracker and reports skipped
- [x] Given a push to the default branch, when the workflow runs, then it finds every merged pull request in the range since the last successful run through the tracker API and reads each Stories: line; and given a push with no associated pull request or no Stories: line, then it posts no merge comment, still mirrors the cards that the push changed, posts one state comment on each issue whose card status changed, and reports the commit SHA
- [x] Given a workflow run that pushes or comments on any story, when the run ends, then `git status --porcelain` in the workflow checkout is empty and the run has pushed no commit (any write-back by `story push` to card files is not committed)

## Out of Scope
- Marking a story done. Only `story-accept` does that; the workflow only mirrors a card that a merge already set done.
- Policing GitHub closing keywords. ST-152's check owns that; this workflow does not parse keywords (a keyword-closed issue is reopened when its card is mirrored, or by the weekly `--all`).
- Trackers other than GitHub in the first slice (Gitea, Azure DevOps next).

## Notes
- Source: owner, 2026-11-16, from Varsity-Engine/varsity-mcp issue #79 and PR #80. #80 merged with no Stories line, and #79 had no ID title prefix or labels until a groom republished it. Within story-time, story issues close today only when an agent runs `story push` after `story-accept`; when that step is skipped, the issue stays open or drifts.
- Shape: a playbook workflow template (`story-sync.yml`, next to `story-link.yml` and `story-ids.yml`) on `push` to the default branch. See the design note below for the mechanism; the comment marker makes reruns idempotent.
- Related: ST-152 (pre-merge check that each named story is done or marked `(partial)`). ST-151 only mirrors cards; without ST-152, a skipped `story-accept` still leaves the issue open with a comment. No dependency either way.
- Design: `docs/designs/merge-sync-design.md` (revision 3). The logic is a new `story sync-merge` verb that calls the gateway `update` directly (no card writes; `story push` unchanged). Runs are serialized and each covers the range since the last successful run; a weekly `--all` is the backstop. A card with no `remote` is skipped as `unlinked`. Trigger is `push` (fork PRs get a read-only token under `pull_request`). AC1 and AC6 amended by design decisions D13 and D16 (revision 3.2: state comment on unnamed status changes, own marker key). Prerequisite: ST-154 (label recolor bug).
- Design brief: `docs/designs/merge-sync.md` (EGM brainstorm, 2026-11-16). Its correction block lists which reviewer premises came from a stale checkout.
- The guidance says not to turn on `sync: auto` in the CLI to publish. This workflow is the CI path for repositories whose policy allows it: it runs only on the default branch, after review and merge, with the repository token.
- Language: the logic is Rust in the story CLI (Article VIII); the YAML is configuration.
- Estimate (PROPOSED by agent): 5; one workflow template, a comment command with an idempotent marker, a reopen path and tests. WSJF values are an agent proposal, not an owner score.
