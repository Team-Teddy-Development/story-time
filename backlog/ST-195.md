## Story
As a team lead, I want a burndown for a sprint (remaining points per day, scope steps, the ideal line, today) and a burnup for an epic or any set of stories, so that I can see during the sprint whether we will finish.

## Source task
2026-11-25, velocity and burndown design (`docs/designs/velocity-burndown.md`, PR #444). Depends on ST-194 (sprint attribute). Eric, 2026-11-25: the figures exist so the delivery dashboard can forecast better, so the JSON is shaped for it.

## Acceptance Criteria
Fixture for every criterion: settings `team.sprints` gives `2026-S01` the dates 2026-11-02 to 2026-11-15. Stories A (size 5), B (size 3) and C (size 2) each have `set sprint=2026-S01` dated 2026-11-01. The command is `story burndown --sprint 2026-S01 --today 2026-11-06 --json` (`native/story-push/src/burndown.rs`, tests in `native/story-push/tests/burndown.rs`).

- [ ] Given the fixture with B done on 2026-11-03, when the command runs, then the row for 2026-11-03 has scope 10 and remaining 7
- [ ] Given the fixture with B done on 2026-11-03 and story D (size 2) given `set sprint=2026-S01` on 2026-11-05, when the command runs, then the row for 2026-11-05 has scope 12 and remaining 9
- [ ] Given the fixture with C given `set sprint=2026-S02` on 2026-11-04, when the command runs, then the row for 2026-11-04 has scope 8 and remaining 8
- [ ] Given the fixture, when the command runs, then `rows` holds 14 rows from 2026-11-02 to 2026-11-15, `ideal` is 10 on the first and 0 on the last, `weekend` is true on exactly 2026-11-07 and 2026-11-08, `today` is true on exactly 2026-11-06, and `remaining` is null on every row after 2026-11-06

## Notes
Decisions:
- **Reads only ST-194's derivations.** The committed set, adds, drops and points at commitment come from ST-194 (design, "Data shape"). Burndown adds no derivation of its own, so the dashboard, `story sprint show` and the burndown can never disagree on scope.
- **Done date.** It is the date of the story's `set status=done` changelog event, parsed as `history()` does (`native/story-push/src/metrics.rs:77-104`). Where a merge hook runs, that event is the merge record: `set status=done — delivered: PR #N (sha)` (ess-monorepo `.github/scripts/ci/story-delivered.js:139-142`; essentials-core `.github/workflows/story-delivered.yml:125` and `:173`). It holds a date, no time. A merge timestamp cannot move a per-day figure, so the burndown stays at day resolution. ST-201 adds `delivered_at` for cycle time, where hours matter.
- **Figures.** Remaining is scope minus the points done on or before the day. Ideal falls in a straight line from the scope on the first day to 0 on the last. Weekend days are rows with `weekend: true`, never dropped (design, "Figures").
- **`--today`.** It defaults to today in the sprint calendar's time zone, and a test passes it so the output is reproducible. Days after it have `remaining: null`.
- **Unsized is unknown, never zero.** This is the `metrics.rs` contract (`metrics.rs:177` and `:194-201`, `unknown` with a reason). The delivery dashboard counts an unsized item as 3 points today (its `forecast` and `burndown` calculations); story-time does not, and ST-203 shows the unknowns instead.
- **Dashboard shape.** The JSON keeps the figure fields of `metrics.rs` (`metric`, `units: "points"`, `window`, `source`, `definition`, `unknown`) and puts one flat object per day in a top-level `rows` array: `day`, `scope`, `remaining`, `ideal`, `weekend`, `today`. A dashboard dataset loads a top-level `rows` array as rows with no loader, so ST-203 can draw it directly.
- **Burnup.** Cumulative points done against total scope for `--epic ID` or `--ids A,B`, over `--from` and `--to`. Rows have `day`, `scope` and `done`.
- **MCP moved out.** `story_burndown` moved to ST-197, which owns every MCP tool and skill of the design. This story is the CLI only.
- **Ship obligations.** New commands go in `story help` and the native command lists of `AGENTS.md` and `README.md` (the `help_contract` and `doc_native_lists` tests).
