## Story
As a backlog coordinator, I want to submit verified acceptance evidence through hosted Story Time so I can accept a merged story without bypassing the hosted write policy. Varsity Core VC-472 (#983) is the observed case: implementation PR #992 merged, but `story_update` cannot tick the existing criteria or write their evidence. Reuse the existing GitHub proposal path, caller authorization, and SHA-256 guard. Keep the existing `story_update` done guard. Out of scope: Gitea, live runner changes, arbitrary section editing, tracker closure before merge, and assignment or WIP changes. ST-174 covers criteria wording, not acceptance.

## Acceptance Criteria
- [ ] Given an authorized caller, an in-progress GitHub-backed story, its current SHA-256, and one nonempty evidence entry per existing criterion, when the caller submits acceptance, then hosted Story Time opens the normal reviewed proposal that ticks the existing criteria without changing their wording, records the evidence, marks the story done, and preserves unrelated content. Main and the tracker remain unchanged until merge.
- [ ] Given a stale SHA-256, missing or duplicate criterion evidence, an ineligible story status, or an unauthorized caller, when acceptance is requested, then the server returns a typed refusal without changing the card, branch, PR, or tracker.
- [ ] Given the hosted tool runs against an isolated forge fixture, when the acceptance proposal lands and the existing tracker sync runs, then the accepted card is on main and the mirrored issue closes as completed. Verify with native Rust hosted-protocol and write-path tests.
