## Story
As a maintainer, I want story plan to use the shared settings validator, so that plan, config, push, and init cannot disagree about whether a settings file is valid.

## Acceptance Criteria
- [x] Given a settings file that config, push, and init reject or accept, when the native binary runs story plan on it, then plan accepts or rejects it the same way and names the same field, verified by a case added to native/story-push/tests/config_agreement.rs

## Evidence
- Red 4dc88b5: config_agreement failed for plan: plan rejected an empty backlogDir that config, push, and init accept ("malformed_data: backlogDir must be a nonempty string or null"), and plan accepted github without repo, which the others reject.
- Green caea73b: native/story-push/src/planning.rs snapshot() calls config::parse; a failure becomes `malformed_config: <reason>`. Removed duplicate checks: tracker and sync lists, team object, prefix pattern, backlogDir and prefix strings, sprintDays and wipLimit integers. Kept plan-only checks: config_conflict for current plus legacy settings, the raw JSON parse for the sha256 source image, safe_path on backlogDir, and the missing-settings input.
- config_agreement now runs `story plan --snapshot` beside config, push --dry-run, and init on every case: accepts agree; on reject plan exits 2 (its conflict protocol) and names the field in stdout, the others exit 1 and name it in stderr. 2 passed.
- Behavior change: with team values absent, plan now reports sprint_days 10 and limit_per_person 1 (the parsed defaults) instead of null. Pinned fixtures changed: an unknown `custom` settings key moved under `jira`, and the malformed-team case became `{"team":{"sprintDays":"ten"}}`.
- Real data: old and new native `plan --snapshot` on this backlog (78 source files, 29 candidates): 0 differences after removing captured_at.
