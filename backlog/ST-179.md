## Story
As a Story Time agent that hits a mid-story blocker, I want MCP tools that label the story blocked, free WIP, propose durable unblock children, and return concrete next-step guidance in every mark/propose response, so that I can keep moving past the wall instead of dead-ending while waiting on a separate groomer.

Ship per `/cursor/stores/self/docs/unblocker-story-tool.md` with locked defaults: label-only `blocked` (no `status: blocked` in v1), label name `blocked`, parent `depends_on` → unblock children with `relates_to` parent, re-groom default `replace_existing_unblocks: false` (refuse when open relates_to-unblocks already exist; `true` replaces that subset), auto-clear when those deps are done plus explicit `story_clear_blocked`, recursive blocked-unblock depth cap 2.

## Acceptance Criteria
- [x] Given an `in-progress` story and valid SHA, when `story_mark_blocked` is called with a reason, then frontmatter `labels` contains `blocked`, status is `ready` when `release_wip` is true, a changelog/note records the reason, rank/assignment/poteto no longer select that id, and the tool response includes concrete `next_steps` that tell the calling agent how to unblock (including calling `story_propose_unblocks` itself rather than waiting idle for a groomer).
- [x] Given a `blocked`-labeled parent, when `story_propose_unblocks` is called with 1..N specs, then N new stories exist, each `relates_to` the parent, parent `depends_on` includes those ids, parent is not `split`, cycles refuse with `dependency_cycle` and write nothing, N > `max_children` refuses with `over_split`, and the response `next_steps` name the created child ids to pull next and when to clear/resume the parent.
- [x] Given all parent `depends_on` are `done`, when `story_clear_blocked` runs (or auto-clear after a dep reaches `done`), then `blocked` is removed from `labels` and the parent is pullable again; clear while required unblock deps remain open refuses with `still_blocked` unless `force`.
- [x] Given `story_list` with a labels filter, when filtering for `blocked`, then only stories whose frontmatter labels include `blocked` are returned; push/render_card mirrors freeform `labels` (at least `blocked`) to the tracker.
- [x] Given a ready story that still has label `blocked`, when rank, assignment, or poteto selection runs, then that parent is skipped; unblock children without the label remain eligible under normal WIP; recursive mark→propose depth beyond 2 is refused with escalation guidance.
- [x] Given Rust tests and real CLI/MCP exercise of mark, propose, clear, cycle refuse, WIP release, and next_steps guidance, when the implementation PR opens, then CI passes and the PR body declares `Stories: ST-179 (#issue)`.

## Out of Scope
- First-class `status: blocked`
- Auto-implementing unblock children
- Using `children` / `status: split` for unblock scaffolding
- Changing sprint-planning capacity math beyond blocked-label non-selection

## Test Plan
1. MCP/unit: `story_mark_blocked` on in-progress → labels+ready+note+next_steps (failing until tool exists).
2. MCP/unit: `story_propose_unblocks` creates N children, wires depends_on/relates_to, returns child ids in next_steps.
3. MCP/unit: propose cycle → `dependency_cycle`, no writes; N > max_children → `over_split`.
4. MCP/unit: `story_clear_blocked` removes label when deps done; refuses `still_blocked` when open; auto-clear path after dep done.
5. Unit: rank/assignment skip `labels ∋ blocked`; list filter by label; render_card/push includes `blocked`.
6. Unit: depth cap 2 refuse with escalation in next_steps/guidance.
7. Integration: exercise tools via MCP test harness (same style as existing `mcp_*.rs` tests).
