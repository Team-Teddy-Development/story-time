## Story
As a team lead, I want a story that a merged pull request names only by its issue number to get one comment on its issue, so that the issue history shows each merge once

## Acceptance Criteria
- [ ] Given a merged pull request whose body has 'Stories: #12' and a card with remote 12 whose status changed from in-progress to done in the range, when `story sync-merge --json` runs, then issue 12 gets exactly one comment, of kind merge, and the report lists no state comment for issue 12
- [ ] Given a push with no pull request that changes the status of a card with remote 12, when `story sync-merge --json` runs, then issue 12 gets exactly one state comment
- [ ] Given the first scenario and the bot's merge marker already on issue 12, when `story sync-merge` runs again, then it posts no comment

## Notes
- Source: EGM drift report on `docs/designs/merge-sync-design.md`, run 2026-11-16 as the trial for a design-deviation brief. Finding DR-08. A second code read at `f3a9dbd` confirmed it. No test was run; write the failing test first.
- Design: `docs/designs/merge-sync-design.md` lines 388-392: a state comment goes only to "a card that no kept PR names".
- Code: `story sync-merge` adds a reference to `named_ids` only when it has a story ID (`native/story-push/src/sync_merge.rs:384-394`). A reference such as `Stories: #12` posts the merge comment on issue 12, but its card is not in `named_ids`, and the state-comment loop uses `changed.difference(&named_ids)` (`sync_merge.rs:465`).
- No contract test covers a bare issue reference whose card changed status in the range. `a_bare_issue_reference_with_no_card_is_unmapped` covers only the unmapped case.
- Related: ST-151 (sync-merge), ST-157 (Gitea sync-merge, same code path).
