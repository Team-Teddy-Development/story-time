## Story
As a client of the hosted story-time MCP, I want story_repos to say when the last fetch of a repository failed, and the server to fetch again on its own, so that I can tell when the backlog I read may be old and it gets current again without my reads.

## Acceptance Criteria
- [ ] Given a repository that the server fetched, when a later fetch fails and a client calls story_repos, then its entry keeps state ready, the sha of the last good fetch, and a non-null last_error, and the story_repos outputSchema is unchanged
- [ ] Given a repository whose last fetch failed, when the forge answers again, then the server fetches it within 2 fetch TTLs with no client read, and story_repos shows state ready, last_error null, and the new sha
- [ ] Given a repository that the server fetched, when no fetch has failed since, then story_repos shows state ready, last_error null, and the sha of the remote default branch

## Out of Scope
- The repair of the cluster DNS (coffee-cluster-talos issue 52).
- The retry inside one fetch (ST-147, done).
- The schema skew of long-lived client sessions (ST-148). A separate `fetch_ok` field waits for it, because the entry schema sets `additionalProperties: false` today.

## Notes
Source: VM-034 (varsity-mcp issue 79). On 2026-11-16 at 03:54Z `story_repos` showed varsity-mcp as `state: ready` with `last_error: git fetch failed: ... Could not resolve host: github.com`. Cause in the code: `publish()` in `native/story-push/src/mcp/workspace.rs` maps every cloned repository to `ready`, whatever the last fetch did. A fetch runs only once at start (`warm`) and then on a read after the TTL, so a failed fetch of a repository that nobody reads stays failed. The DNS fault is coffee-cluster-talos issue 52; ST-147 retries 4 times in one fetch.

Decision (2026-11-16, Jev, owner-delegated): keep `state: ready` and report the failure beside it, not a new state `stale` (option A) and not `unavailable` (option B). Jev chose C_boolean_beside_ready (jev-1.14.0, confidence 0.46, a low confidence; probabilities C 0.64, A 0.20, B 0.16). Its reason: a new enum value breaks long-lived MCP client sessions until they restart (ST-148). This replaces the earlier decision for `stale`, which the loop agent made without Jev at confidence 0.8.

Implementation of C: the signal beside `ready` is the existing `last_error`, not a new `fetch_ok` field. `repos_schema()` builds each entry with `additionalProperties: false`, so a new field breaks the same old sessions as a new enum value (the ST-148 error is `must NOT have additional properties`). `last_error` is already in the schema, so this change does not change the schema. A `fetch_ok` boolean can follow after ST-148. A background loop (`keep_fetched`) fetches each repository once per fetch TTL.
