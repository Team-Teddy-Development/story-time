## Story
As a story-time maintainer, I want the hosted workspace test of a private repository to pass on a loaded machine, so that a full test run does not fail for a reason that is not a defect of the change.

## Acceptance Criteria
- [ ] Given 96 runs of the test a_private_repository_is_fetched_with_an_installation_token_that_no_output_shows, 24 at a time, when each one finishes, then each one exits 0 in less than 20 seconds

## Notes
Found on 2026-11-16 during ST-141, on `origin/main` code paths that ST-141 does not change. Fingerprint: `a_private_repository_is_fetched_with_an_installation_token_that_no_output_shows` panics at `tests/mcp_hosted_workspace.rs:269` with `left: 504, right: 200`.

Evidence: one failure in a full `cargo test --locked` run that started right after clippy; the same file passed alone (7 passed, 4.4 s) and in a second full run. Reproduced with 24 copies of the test binary at the same time: 3 of 24 exited non-zero, each with this panic, after about 33 s.

Cause: the first tool call of that test makes the server clone the repository from the stub and get an installation token. The HTTP front answers 504 `request timed out` when a call takes longer than `--request-timeout-seconds`, default 30 (`src/mcp/http.rs`). On a loaded machine the first call takes longer than 30 s. The test asserts status 200 for each call. Not decided: give the test server a longer deadline, or make the test wait for `story_repos` to report `ready` before its first read.

Correction (2026-11-16, later the same day). The cause above is wrong: load is not necessary.
- The same failure broke the `native-push` check of PR #324 in GitHub CI (run 43796061075): the test file finished in 30.15 s with `left: 504`.
- It is older than ST-141: on `12ffe40`, the commit before ST-141, 4 of 48 runs of this one test failed (24 at a time, two rounds).
- The run times have two groups: a run that passes takes 1 to 2 s, and a run that fails takes 30 to 31 s. So the first `story_show` call does not run slowly; it hangs until the 30-second deadline.
- In a failing run the server log holds only `listening on ...`, also 8 s after the 504: no audit line and no `fetch_failed` line. The call waits on the first clone of the repository, and that clone does not end. It goes through the installation token request and then `git` over the dumb HTTP protocol, both against the `tiny_http` stub of the test.
- Not found: which of the two requests hangs, and if the stub or the server is at fault. The first clone on the real cluster against GitHub succeeded (ST-136).
- A fix needs the point of the hang first. Rate seen: 3 of 24, 4 of 48, and 2 of 72 parallel runs; 1 of 2 full local runs; 1 CI run.

Root cause (2026-11-16, found with `GIT_TRACE_CURL` and a log of the stub). The stub of the test is a `tiny_http` 0.12.0 server. `git remote-http` opens several connections at almost the same time. In a failing run, `git` sends a request on a new connection, and `tiny_http` gives that request to the stub 30 s later. Its thread pool (`src/util/task_pool.rs`) loses a wakeup:
- `spawn` queues a task and calls `notify_one` when `waiting_tasks` is not 0.
- A worker that an earlier `notify_one` woke is still counted in `waiting_tasks` until it gets the lock again.
- A second `spawn` in that window queues its task for a worker that is not waiting. The task stays in the queue until a worker finishes a connection or a later connection arrives.
`Connection: close` on each answer did not remove the failure (7 of 192). `tiny_http` 0.12.0 is the newest release, so the fix replaces the stub of this test with a small server on `std::net::TcpListener` that has one thread for each connection.

The HTTP front of the product (`src/mcp/http.rs`) uses the same `tiny_http` pool. ST-144 records that exposure; it is not part of this story.

## Test Plan
- The criterion: build `tests/mcp_hosted_workspace.rs`, run the test binary with the filter `a_private_repository` 96 times, 24 at a time, and read each exit code and each `finished in` time.
- Control: the same loop on `origin/main` before the fix gives failures (4 of 48, 2 of 72, 6 of 96, 3 of 96 seen).
- Regression: `cargo test --locked --test mcp_hosted_workspace` passes 7 of 7; the assertions of the test on the requests that the stub saw do not change.
