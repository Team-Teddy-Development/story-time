## Story
As a maintainer of an existing project, I want a brownfield adoption and upgrade path, so that I can use the lifecycle version of story-time without rebuilding or losing the project's existing backlog.

## Acceptance Criteria
- [ ] Given an existing backlog and repository configuration, when adoption preview runs, then it reports source and target versions, an ordered migration plan, preservation rules, and unresolved conflicts without changing project or tracker state.
- [ ] Given an approved migration plan with a verified backup, when migration applies, then story IDs, tracker identities, custom fields, dependencies, estimates, statuses, closed records, acceptance criteria, and evidence remain preserved unless an explicit reviewed mapping changes them.
- [ ] Given the same project and migration version after a successful apply, when adoption runs again, then it creates no duplicate stories, issues, labels, or migration changes.
- [ ] Given ambiguous records, changed preimages, unsupported tracker capabilities, or a failed migration step, when apply or rollback runs, then it preserves recoverable project state and reports each unresolved conflict and recovery action without claiming success.
- [ ] Given legacy stories without current sprint goals, capacity, epic relationships, or authoritative event history, when adoption completes, then it retains those stories and records missing or unsupported data without inventing history or forcing completed work through the new workflow.

## Scope
Extend the existing `story-setup` owner with distinct new-project, adopt-existing, and upgrade-existing paths. Reuse existing story editing, readiness, epic mapping, and tracker adapters. Implement retained migration logic and tests in Rust. Define the target data/schema and skill-package versions explicitly before implementation; do not present a proposed CLI name as an installed command.

## Out of Scope
Do not delete, renumber, silently merge, or reopen legacy stories. Do not overwrite repository-specific prefixes, backlog paths, sync policy, Ready/Done rules, custom fields, or credentials. Do not replace the issue tracker, fabricate delivery history, or migrate signing keys into the agent session. Unsupported input requires a preservation-first handoff, not automatic conversion.
