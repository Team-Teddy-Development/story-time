## Story
As an agent operator running story mcp --write, I want story push to take the repository lock before it writes remote back, so that a push never silently replaces an MCP update.

## Acceptance Criteria
- [x] Given another process holding the repository write lock, when story push writes remote and remote_url back into a story file, then it waits up to the CLI lock wait and then exits non-zero without changing any story file and without creating or updating a tracker item, and once the lock is free the push succeeds, verified by a native/story-push test with a fake tracker that holds the lock during the push

## Notes
Source: ST-116 (PR #262) agent report and Jev review (push_unlocked, 0.58). ST-116 locked set, note, new and split. The native story push still writes remote and remote_url back into story files with no lock, so it can race an MCP story_update. Open question for the implementer: take the lock only around the write-back, or around the whole push, so the tracker call and the file stay consistent. Native init and install-skills also take no lock, but they do not write story files.

## Evidence
- Criterion 1: `native/story-push/tests/closed_pending_create.rs` `push_waits_for_the_repository_lock_before_touching_the_tracker_or_stories` uses that file's fake Gitea tracker.
  - It holds the root lock while `story push` runs, and asserts exit 1, empty stdout, the `lock_for_write` message, an unchanged byte-and-mode snapshot, and no tracker writes.
  - After the lock is released, the same push succeeds with writes `["PATCH 7", "POST 7 labels"]` and `remote: 7` written back.
- Red (f969254): with the lock held, push exited 0, updated tracker item 7 and wrote `remote` back.
- Green (d2e51d8): `push()` in lib.rs takes `adoption_apply::lock_for_write` after the flag and tracker checks and before `plans()` reads the stories, and holds it through the tracker calls, the write-back and any rollback.
  - `--dry-run` writes nothing and takes no lock: `story push --dry-run` under `flock -n .` exited 0.
  - No write command starts a push, so the lock cannot wait on itself.
- Checks on the rebased branch (main 22c2a95, with ST-120): fmt ok; cargo 73 binaries, 372 passed, 0 failed; npm pass 457 fail 0; story-policy 12 passed; contract 11 passed.
- Real data: `push --all --dry-run --json` on this backlog (119 stories), Node against native (PATH=/nonexistent): identical output, both exit 0.
