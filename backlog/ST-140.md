## Story
As a coding agent, I want the hosted story-time MCP to read repositories on Gitea as it reads repositories on GitHub, so that Team Teddy stories on Gitea have the same list, show, lint, and config tools.

## Acceptance Criteria
- [ ] Given a registry entry with forge = "gitea" and a clone URL that the entry permits, when the server starts, then story_repos lists the repository as ready with a sha and fetched_at, and story_list, story_show, story_lint, and story_config read it
- [ ] Given a private Gitea repository and --gitea-token-file, when the server fetches it, then git gets the token only through the child environment, and the token is in no URL, argument, log line, or tool result
- [ ] Given a Gitea entry with an http clone URL and no allow_http = true, or a GitHub entry with allow_http, when the server starts, then it exits non-zero and names the entry
- [ ] Given a registry entry with an unknown forge value, when the server starts, then it exits non-zero and names the entry and the permitted values github and gitea
- [ ] Given a registered Gitea repository, when a write tool or a comment tool is called for it, then the server returns the tool error forge_not_supported, pushes nothing, and sends no request to the forge

## Out of Scope
- Writes and pull requests on Gitea (ST-149). Tracker comments on Gitea (ST-150).
- A change to the GitHub path.
- More than one Gitea host on one server. One token file serves each Gitea entry.
- TLS in front of Gitea. The entry flag covers plain HTTP.

## Notes
Source: owner message on 2026-11-16, "then next story is support for gitea", after the hosted server went live for the GitHub repositories of Varsity (ST-136). Refined on 2026-11-16 at the owner's request ("groom it first").

Split (Jev: three stories, 0.63): this story is the read slice. ST-149 is writes and pull requests. ST-150 is comments. Each is accepted alone.

Decisions:
- Plain HTTP (Jev: entry opt-in, 0.95). The server sends a token only to `https` today (`target` in `mcp/forge_auth.rs`). The Gitea of the team has no TLS: `http://gitea.gitea.svc:3000` in the cluster and `http://192.168.1.56:30003` on the LAN. A Gitea entry can set `allow_http = true`. The default stays https only, and a GitHub entry cannot set the flag.
- Credential. Gitea has no App installation token. The credential is an access token of a bot user, read from the file that `--gitea-token-file` names. Git gets it as an HTTP header through the child environment, as the GitHub token does (`access` in `mcp/forge_auth.rs`).
- Orgs. The registry holds several orgs now (ST-141), so the Gitea repositories can be an org of their own, and ST-142 can limit a client to it.

Facts read on 2026-11-16: `GET http://192.168.1.56:30003/api/v1/version` returns 200. `team-teddy/xanthos` is public there with the default branch `main`, so the read of `xanthos` needs no token. The registry parser refuses `forge = "gitea"` today (`mcp/registry.rs`).

Owner handoff for the cluster (not a criterion of this story): make a Gitea bot user and its token, and put the token in Vault. A public repository such as `xanthos` reads without it.

## Test Plan

- Criterion 2: the same file, with the stub that serves a repository only to a request with the token. The test reads stderr and each tool result for the token. Unit test of the git environment in `src/mcp/forge_auth.rs`.
