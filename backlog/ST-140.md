## Story
As a coding agent, I want the hosted story-time MCP to serve repositories on Gitea as it serves repositories on GitHub, so that Team Teddy stories on Gitea have the same read, edit, link, and comment tools.

## Acceptance Criteria
- [ ] Given a registry entry with forge = "gitea", a base URL, and a token file, when the server starts, then story_repos lists the repository as ready with a sha and fetched_at, and the token is not in a URL, an argument, a log line, or a tool result
- [ ] Given a registered Gitea repository, when story_update runs with the current sha256, then the server pushes the commit to story-time/<ID>, opens one Gitea pull request, and returns its pr_url
- [ ] Given a story with a Gitea issue, when story_comments and story_resolve_comment run, then the comments return with resolved state and the reply carries the story-time marker
- [ ] Given a registry entry with an unknown forge value, when the server starts, then it exits non-zero and names the entry and the permitted values

## Out of Scope
- A change to the GitHub path.
- Links between a GitHub org and a Gitea org. The registry holds one org.

## Notes
Source: owner message on 2026-11-16, "then next story is support for gitea", after the hosted server went live for the GitHub repositories of Varsity (ST-136). The server reaches a forge in three places today: the clone and push credential (`mcp/forge_auth.rs`, a GitHub App installation token), pull requests and comments (`mcp/forge.rs`, GitHub REST), and the bot identity that marks a comment resolved. Gitea has no App installation token, so the credential is a token of a bot user, from a file. The local Gitea is `http://192.168.1.56:30003`; in the cluster it is `http://gitea.gitea.svc:3000`, which is plain HTTP, and the server sends a token only to `https` today. Refinement must decide that rule. This story has four criteria over three areas (read, write, comments); refinement can split it along those areas.
