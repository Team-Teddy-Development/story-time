## Story
As an agent operator running story mcp --write next to CLI commands, I want MCP writes to wait briefly for the repository lock, so that a write that overlaps another writer by milliseconds is not refused.

## Acceptance Criteria
- [x] Given another writer that holds the repository lock and releases it within the CLI lock wait, when story_update, story_note or story_create runs, then the write succeeds after the lock is free, and when the lock is held past the wait the result is lock_held with no file changed, verified by native/story-push tests/mcp_protocol.rs, which passes 20 of 20 full parallel runs

## Notes
Source: ST-119 agent report and coordinator reproduction on main 8286330 (bb24efc). tests/mcp_protocol.rs story_create_refuses_a_duplicate_title_unless_it_is_allowed failed 8 of 20 parallel runs and 0 of 20 single-thread runs, with lock_held at line 1377 after the test dropped its lock. Cause: the test holds the flock on an open file description; a child forked by another test thread holds a copy until exec, so the lock outlives drop for a moment, and the MCP server tries the lock once. Since ST-116 the CLI waits up to 3 s (adoption_apply::lock_for_write); MCP Server::lock does not wait. Fix: one shared bounded wait for both.

## Evidence
- Criterion 1: `tests/mcp_protocol.rs` `write_tools_wait_for_a_writer_that_finishes` holds the root lock and releases it after 300 ms while `story_update`, `story_note` and `story_create` each run. Each one succeeds. The existing `lock_held` assertions still pass: a lock held for the whole wait still returns `lock_held`, with the snapshot unchanged.
- The full `mcp_protocol` binary run in parallel: on main (bb24efc), 8 of 20 runs failed (`story_create_refuses_a_duplicate_title_unless_it_is_allowed`, lock_held after drop), and on one thread 0 of 20 failed. After the fix, 0 of 20 parallel runs failed.
- Red: the new test got `lock_held` at once. Green: `adoption_apply::wait_for_lock` retries `try_lock` for up to `WRITE_LOCK_WAIT` (3 s). `lock_for_write` (CLI) and `Server::lock` (MCP) both use it. The MCP message is "Another process held the repository write lock for 3 seconds."
- Checks on the rebased branch: fmt ok; clippy clean; cargo 73 binaries, 371 passed, 0 failed; npm pass 457 fail 0; story-policy 12 passed; contract 11 passed.
