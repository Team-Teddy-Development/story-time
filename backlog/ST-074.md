## Story
As a maintainer, I want settings validation to reject tracker fields that are not strings, so that a dry run fails on the same settings that a real push rejects.

## Acceptance Criteria
- [x] Given settings with a non-string tracker field such as ado.organization 5 or github.repo ["acme/shop"], when the native binary runs story config or story push --dry-run, then it exits 1 and names the field, verified by a case in native/story-push/tests/config_agreement.rs

## Evidence
- Red 03bb177: native accepted `{"github":{"repo":["acme/shop"]}}` and similar settings (the Node half of the new contract case passed, confirming Node accepts them).
- Green f1b3e47: config::parse rejects a non-string github.repo, ado.organization, ado.project, gitea.baseUrl, gitea.owner, or gitea.repo with "<field> must be a string."; parsed output holds the string values. The `g.baseUrl.replace is not a function` copy of Node's TypeError is deleted.
- config_agreement has 6 new reject cases, checked against config, push --dry-run, plan, and init. config_contract `non_string_tracker_fields_reject_settings_node_accepts` records the intended divergence from Node (5 cases). config_agreement 2 passed, config_contract 10 passed.
- Native `story config` and `story push --all --dry-run` on this repository's real settings exit 0; native and Node `config --json` on the real settings are byte-identical.
- Checks after rebase on main 7f2790e: as ST-073 (205 passed, 41 binaries; npm 456/456; story-policy 12 and 11).
- Follow-up: ST-078 (a non-string prefix passes config::parse).
