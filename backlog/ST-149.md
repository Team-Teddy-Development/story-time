## Story
As a coding agent, I want story_update, story_note, and story_create to work on a registered Gitea repository, so that a story edit on Gitea reaches review as one pull request, as it does on GitHub.

## Acceptance Criteria
- [ ] Given a registered Gitea repository and a bot token with write access, when story_update runs with the current sha256, then the server pushes one commit to story-time/<ID>, opens one Gitea pull request, and returns its pr_url
- [ ] Given a story that has an open story-time pull request on Gitea, when a second edit runs, then the server adds a commit to the same branch and opens no second pull request
- [ ] Given a registered Gitea repository, when story_create or story_note runs, then the result has the same fields as on a GitHub repository
- [ ] Given a bot token that Gitea refuses, when a write tool runs, then the server returns forge_unavailable with the failed step, and the token is in no log line and no tool result

## Out of Scope
- Comments (ST-150).
- A merge of the pull request. A person merges it.
- A change to the GitHub path.

## Notes
Source: split of ST-140 on 2026-11-16 (Jev: three stories, 0.63). ST-140 is the read slice and gives the token file and the `allow_http` rule.

The server reaches the forge for writes in `mcp/forge.rs` (GitHub REST: find the open pull request of a branch, create a pull request) and in `mcp/workspace.rs` (push with lease; the commit author email has the form `<author>@users.noreply.github.com`). Gitea has the same two calls under `/api/v1/repos/{owner}/{repo}/pulls`. The author email of a Gitea commit needs a form that is not of GitHub.

Owner handoff: the bot user needs write access to each served Gitea repository. Verification of criterion 1 on the real Gitea needs that token.

Live check: one story edit on a scratch repository of the real Gitea with the bot token.
