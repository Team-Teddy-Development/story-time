## Story
As a team lead planning with story-time, I want each story's estimate, and the completion dates forecast from burndown and velocity, to be corrected by how long similar stories actually took, so that the dates I commit to get closer every sprint.

## Source task
2026-11-25, Eric: "we now have burn down and velocity so i would like these completion dates closer. Plan how to do that better using either Jev or maybe Opus when doing estimation. Maybe a learning layer to get better with every estimation of estimated vs shipped time."

## Today
- `story-estimate` sizes with simulated planning poker anchored on reference stories.
- `story judge` (`native/story-push/src/judge.rs`) asks Jev, or falls back to a code heuristic that sizes from criteria count alone. On ESS-390 it suggested 8 at confidence 0.3, against a poker size of 2.
- `story metrics` (`native/story-push/src/metrics.rs`) reports throughput, WIP and median cycle time.
- Nothing compares an estimate with what happened, so the same bias repeats every sprint.

## Plan (to refine in grooming)
1. **Record every estimate as a prediction.** When a story goes ready, store the size, the estimator that produced it (poker, Jev, Opus, code), its confidence and the features it saw: type, repo, criteria count, files or paths named, and whether the Dark Factory or a person builds it. Store it in the story frontmatter or a sidecar ledger, never in the issue body.
2. **Record the outcome.** When a story is done, take the actual cycle time (ready to done, from story history and the merged PR), the number of PRs, and re-opens. Factory-built and person-built stories are separate populations: factory cycle time is minutes, a person's is days.
3. **Learning layer, deterministic.** Per repo and population, keep the distribution of actual cycle time per size and a bias factor per feature, such as "size 2 stories with migrations take 2.4 times the median". Recompute it on each `story metrics` run. This is plain statistics in code, so it is reproducible and needs no model.
4. **Forecast dates by simulation, not by points alone.** Replace "points divided by velocity" with a Monte Carlo over historical throughput and the calibrated per-size cycle times. Report the 50% and 85% completion dates for a sprint, an epic or a burndown line, and show how wide the range is.
5. **Model estimators, scored.** Jev and Opus each predict a size bucket from the story text. Every estimator, including poker and the code heuristic, is scored on closed stories (mean absolute error of predicted against actual bucket, plus calibration of its confidence). `story-estimate` then uses the best-scoring estimator per repo and population as its prior, with the others as dissent.
   - Jev masks every digit, so it can answer only categorical buckets and never numeric durations. The arithmetic stays in code.
   - Opus can read the codebase and the anchors, so it is the better estimator for work that is unclear about which files it touches.
6. **Feedback in the loop.** `story-accept` writes the actual time and the error. `sprint-review` and `retrospective` show "estimated against shipped" for the sprint and the biggest misses, and the bias factors update.

## To plan
- Where the ledger lives: frontmatter fields, `.story-time/estimates.jsonl`, or the hosted server.
- The minimum history before calibration replaces the raw estimate (for example 20 closed stories per population). Until then, show raw and calibrated side by side.
- Whether Opus estimation runs through the hosted server or the local skill, and its cost per estimate.
- Privacy: no PII in features. Jev and Opus see the title, statement and criteria only, with names listed as sensitive terms.
- Backfill: compute actuals for stories already done, from git history, to seed the model on day one.

## Acceptance Criteria
- [ ] Given 20 or more closed stories in a repo with recorded estimates and actual cycle times, when story metrics forecasts a sprint, then it reports 50% and 85% completion dates from the calibrated model and each estimator's error on the closed stories
