## Story
As a team lead planning with story-time, I want each closed story's estimate set against how long it actually took, grouped by size, builder and repository, so that forecasts and the delivery dashboard can correct for how we really deliver and the dates I commit to get closer every sprint.

## Source task
2026-11-25, Eric: "we now have burn down and velocity so i would like these completion dates closer. Plan how to do that better using either Jev or maybe Opus when doing estimation. Maybe a learning layer to get better with every estimation of estimated vs shipped time."
2026-11-25, Eric: "estimation and actuals are recorded on PR merge", and the goal is "estimation vs actual so we can use our dashboard for better forecasting".

## Today
- `story-estimate` sizes with simulated planning poker anchored on reference stories.
- `story judge` (`native/story-push/src/judge.rs`) asks Jev, or falls back to a code heuristic that sizes from criteria count alone (`judge.rs:398`, confidence 0.3 at `:487`).
- `story metrics` (`native/story-push/src/metrics.rs`) reports throughput, WIP and median cycle time.
- Nothing compares an estimate with what happened, so the same bias repeats every sprint.

## Acceptance Criteria
Code in `native/story-push/src/estimates.rs` for `story estimates [--json]`, the `built_by` field in `set.rs` and `lint.rs`. Tests in `native/story-push/tests/estimates.rs`.

- [ ] Given a story with changelog lines `2026-11-02 set size=3`, `2026-11-03 set status=in-progress` and `2026-11-07 set status=done — delivered: PR #12 (abc1234)`, when `story estimates --json` runs, then its row equals `{"id": "ST-001", "estimate": 3, "start": "2026-11-03", "start_event": "in-progress", "done": "2026-11-07", "actual_days": 4, "built_by": "unknown", "pr": 12}`
- [ ] Given a done story with no in-progress event, `set status=ready` on 2026-11-01 and `set status=done` on 2026-11-05, when `story estimates --json` runs, then its row has `start_event` `ready` and `actual_days` 4
- [ ] Given a story with `set size=2` on 2026-11-02, `set status=in-progress` on 2026-11-03, `set size=5` on 2026-11-04 and `set status=done` on 2026-11-06, when `story estimates --json` runs, then its row has `estimate` 2
- [ ] Given a story, when `story set ST-001 built_by=robot` runs, then it exits 1 with `built_by must be factory or person` and the file is unchanged
- [ ] Given 12 done size-2 stories with `built_by: factory` and actual days 1 to 12, when `story estimates --json` runs, then `groups` holds `{"size": 2, "built_by": "factory", "level": "size_builder", "n": 12, "median_days": 6.5, "p85_days": 11}`
- [ ] Given 4 done size-5 stories with `built_by: person` and 7 with `built_by: factory`, when `story estimates --json` runs, then the group for size 5 and `person` has `level` `size` and `n` 11

## Notes
Decisions (settling the To-plan questions):
- **No new ledger. The estimate and the outcome are already on the story.** The merge hooks set a story done when its pull request merges, as one changelog line `set status=done — delivered: PR #N (sha7)`: ess-monorepo `.github/scripts/ci/story-delivered.js:139-142` writes it directly, and essentials-core `.github/workflows/story-delivered.yml:125` and `:173` writes it through `story set`. Story-time itself has no merge hook; `story-accept` writes its done line. What the merge writes is a date, the PR number and the commit. It writes no estimate, no duration, no time of day and no builder. The estimate is already in the changelog as `set size=` lines. So this story reads both from the changelog and adds no recorder.
- **The part the merge hook lacks is filled at the same hook, not by a second recorder.** ST-201 extends those two hooks to write `delivered_at` (the PR's merge time) and `built_by` (`factory` when the head branch starts with `factory/`, as the Dark Factory's branches do, for example `factory/auto/abc` in ess-monorepo `api-service/app/src/views/internal/dark-factory/fixBuildGate.test.ts:52`; otherwise `person`). This story only makes `built_by` a valid attribute, so the hooks can write it, and reads it. Following Eric's direction for sprint, it is a story attribute so the MCP can use it. Until ST-201 lands, `built_by` is `unknown`.
- **Estimate.** The last `set size=` on or before the start event, so a re-estimate after work starts does not rewrite the prediction (the same rule as ST-194's points at commitment).
- **Actual.** Days from the first `status=in-progress` event to the first `status=done` event. With no in-progress event, the first `status=ready` event is the start, and `start_event` says which. This matters: in ess-monorepo, 0 of 122 sized done stories have an in-progress event (they go ready to done through the factory), against 136 of 139 in story-time and 136 of 183 in essentials-core (counted on each `origin/main`, 2026-11-25).
- **Calibration groups.** Jev, 2026-11-25 (0.74; runner-up size by builder, 0.17): group by size, builder and repository. A group too small falls back to size by builder, then to size alone. `story estimates` reads one repository, so locally the first level is size by builder within it and the fallback is size within it. The middle level, size by builder across repositories, exists where several repositories' rows meet: the hosted `story_estimates` (later) and the dashboard (ST-203).
- **Minimum history: 10 closed stories per group.** Below 7, the nearest-rank 85th percentile is the group's maximum (rank 6 of 6), so the 85% figure would be the worst case and not a percentile. At 10 it is the 9th of 10. Closed sized stories per size on `origin/main` (2026-11-25): story-time 51, 35, 29, 19, 5 for sizes 1, 2, 3, 5, 8; ess-monorepo 31, 52, 31, 8 for sizes 1, 2, 3, 5; essentials-core 31, 46, 59, 35, 8 for sizes 1, 2, 3, 5, 8; ess-ai-control-plane 10 in all. So with 10, sizes 1 to 3 keep their own groups even if the builder splits them in half, and sizes 5 and 8 fall back. A smaller group reports `level: "none"` with the count, and its stories stay uncalibrated, never zero.
- **Backfill.** None is needed for estimates and actuals: the changelogs above already give 400 or more closed stories with both, so calibration works on day one. Backfilling `built_by` and `delivered_at` for stories merged before ST-201 reads the PR number in each delivery line; that belongs to ST-201.
- **Opus estimation, cost and placement.** Decided for ST-199: Opus runs in the local `story-estimate` skill as one more poker voice, under the user's own Claude subscription, so it adds no per-call charge to story-time. The hosted server makes no model calls and holds no model credentials (ADR 0007). Jev's cost per call is already reported by `story judge` (`judge.rs:326`). Jev masks every digit, so it may answer size buckets but never durations; the arithmetic stays in code.
- **Dashboard shape.** `story estimates --json` puts one flat object per closed story in a top-level `rows` array, which a dashboard dataset loads with no loader, and the groups in `groups`. ST-203 draws "estimated against shipped" from it.

Slices of the original plan:
- This story: steps 1 to 3 (estimate, outcome, deterministic learning layer).
- ST-198: step 4, the forecast draws calibrated samples.
- ST-199: step 5, Jev and Opus estimators, scored.
- ST-200: step 6, sprint review and retrospective show estimated against shipped.
- ST-201: the merge hooks record `delivered_at` and `built_by`.
- ST-203: the delivery dashboard panels.
- **Ship obligations.** New commands go in `story help` and the native command lists of `AGENTS.md` and `README.md` (the `help_contract` and `doc_native_lists` tests).

Estimate: see the changelog line for the poker votes and anchors.
