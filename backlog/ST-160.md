## Story
As the owner, I want the hosted story-time server to start with the token of the Gitea bot user from Vault, so that it reads private Gitea repositories and is prepared for Gitea writes (ST-149) and comments (ST-150).

## Acceptance Criteria
- [ ] Given the Vault entry global/infra.story-time.gitea-token and the deployment flag --gitea-token-file, when the pod starts, then story_repos on the live server shows the Gitea repository xanthos as ready, and the token is in no log line of the pod and no tool result

## Out of Scope
- Writes and pull requests on Gitea (ST-149). Comments on Gitea (ST-150).
- A new Gitea repository in the registry. The owner names each one.

## Notes
Source: owner request on 2026-11-16 ("can you use my gitea token to configure what you need").

Done on the Gitea with the owner token: team `story-time-bot` (id 14) in the org `team-teddy`, write on code, issues, and pulls, with only the repository `xanthos`; the user `story-time-bot` is its member; the bot has a token `story-time-mcp` with the scopes `write:repository` and `write:issue`. The token and the bot password are in mode-600 files under `~/.config/story-time/` on the owner machine.

No private Gitea repository has story-time settings on 2026-11-16 (119 repositories examined). The check thus uses `xanthos`: Gitea refuses a wrong token on a public repository also, so `ready` shows that Gitea accepts the token.

Changes are in coffee-apps: `scripts/provision-story-time-secrets.sh` (a mode that writes only the Gitea token), `k8s/story-time/20-externalsecret.yaml`, `k8s/story-time/30-deployment.yaml`. Order: the script change merges, the owner runs the script, then the ExternalSecret and the deployment change merge. The other order stops the start of the pod, because the token file does not exist.

Owner handoff: an agent cannot write to Vault. The owner runs the script.
