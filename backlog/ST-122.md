## Question
Which Loki, VictoriaMetrics, Tempo and Grafana deployments already exist for Team Teddy, who owns them, and how would a story-time process send them data?

## Exit Criteria
- [x] Given read-only access to the Team Teddy cluster and its docs, when the inventory runs, then docs/spikes/ST-122-observability-inventory.md records for Loki, VictoriaMetrics, Tempo and Grafana the deployment owner, endpoint, collector, authentication method and retention, or states that the item could not be found, with the command or document that showed each fact

## Notes
Source: ST-008 Notes require this inventory before readiness; Jev decision 2026-11-14 (jev-1.14.0, owner said 'jev decide'): run a read-only inventory spike (0.97). Read only: no deploy, no config change, no credential read. Answers ST-008, ST-009 and ST-010.

## Findings
Answer: one stack exists, namespace `drip` on the coffee cluster, owned by the Argo CD Application `drip-observability` (team-teddy/coffee-apps `k8s/drip`). It has an OTel Collector (OTLP/HTTP, bearer token), Loki (14 days), Tempo (7 days), VictoriaMetrics (90 days, scrapes the collector, keeps only listed metric prefixes) and Grafana with linked datasources. The Xanthos gateway forwards OTLP from GitHub Actions with OIDC. Evidence, per-cell sources and recommendations: docs/spikes/ST-122-observability-inventory.md.

Decision (recorded in the spike doc's Decision section): export only through the Xanthos gateway from GitHub Actions, telemetry off unless configured, developer-machine runs out of scope, `story_time_` metric prefix.

Follow-ups: ST-008, ST-009 and ST-010 are refined with tests and sizes; ST-123 (coffee-apps keep regex, a deploy that waits for the owner) is filed and ST-009 depends on it.

Unmet or unchecked: no live OTLP send was made (it needs the bearer token or a CI run); Xanthos payload format handling and Grafana permissions were not checked; NetworkPolicy enforcement was inferred, not tested.
