## Story
As a story-time operator, I want one hosted server to hold the repositories of several orgs, so that Varsity and Team Teddy use one deployment and each org keeps its own backlog and links.

## Acceptance Criteria
- [ ] Given a registry with two [[org]] tables that each hold repositories, when the server starts, then story_repos lists every repository with its org, and a registry in the current one-org format still loads with no change
- [ ] Given two orgs that each have a story VC-001 or use the same prefix, when story_show names the org or the repository, then it returns the story of that org, and a call that matches two orgs returns an error that names both
- [ ] Given two orgs in the graph, when story_graph runs for a story of one org, then no node or edge of the other org is in the result
- [ ] Given a registry where one repository key appears in two orgs, when the server starts, then it exits non-zero and names the key

## Out of Scope
- Links between stories of two orgs. A link stays inside one org.
- A second forge type. ST-140 adds Gitea.
- Self-service sign-up. The operator still edits the registry.

## Notes
Source: owner message on 2026-11-16, "maybe not full public but at least we need to support multi org and multi type", after the hosted server went live for one org (ST-136). Today the registry has one top-level `org` value (`k8s/story-time/25-configmap.yaml` in coffee-apps holds `org = "varsity"`), and the design `docs/designs/hosted-story-mcp.md` says one org for each server. The GitHub App `story-time-mcp` is owned by Team-Teddy-Development and can be installed on more orgs, so the credential side already permits several GitHub orgs. "Multi type" is the forge type: ST-140 covers Gitea. ST-142 limits what a client token can read, and it must land before a second org with other readers goes live. The design document needs an amendment for this story.
